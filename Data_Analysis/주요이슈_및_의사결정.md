### D3. [H5] RevIN(N7)을 전처리 파이프라인에 넣을 것인가, 모델 레이어로 넣을 것인가

**현황:**

`Analysis_Plan.md`는 N7 RevIN을 N1-N6과 동일한 "정규화 방법 7종" 테이블에 포함시킴. 그러나 RevIN은 구조적으로 다름:

| 특성 | N1~N6 (현행 코드) | N7 RevIN |
|------|-----------------|---------|
| 구현 위치 | `02_normalizers.py` — numpy/pandas 클래스 | PyTorch `nn.Module` |
| 적용 시점 | 데이터 로드 후, 모델 학습 전 | 모델 `forward()` 내부 |
| 통계 계산 기준 | 학습 통계 사전 계산 후 고정 | 각 추론 배치/윈도우마다 동적 계산 |
| 실험 루프 호환성 | `normalizer.fit()` → `transform()` | 별도 `LSTMWithRevIN` 모델 클래스 필요 |

**만약 RevIN을 N1~N6과 동일한 파이프라인에 놓으면:** 실험 루프 코드가 N7만 특수 분기 처리해야 하며, RevIN의 핵심 특성(추론 시 window별 동적 정규화)이 손상됨.

**옵션:**

| 선택지 | 구현 방식 | 영향 |
|--------|---------|------|
| A. **모델 레이어 분리** | `03_lstm_model.py`에 `LSTMWithRevIN` 별도 클래스 | 실험 루프에서 N7은 `normalizer=None, use_revin=True` 경로 |
| B. **N1~N6을 모두 모델 레이어화** | 모든 정규화를 model forward 내부로 이동 | 코드 대규모 재설계 필요, 불필요한 복잡성 |
| C. **RevIN을 전처리로 근사 구현** | 각 window의 통계로 numpy 전처리 (학습 불가) | RevIN 핵심 특성(학습 가능 γ·β) 손실, 비교 타당성 저하 |

**권장:** A. 실험 루프 코드에 `if normalizer == 'revin': ...` 분기 1개 추가로 해결 가능. RevIN의 학습 가능한 affine 파라미터를 보존해야 N7 결과가 의미 있음.

> **✅ 결정 완료 (2026-07-02):** A 선택 — N7 RevIN은 `03_lstm_model.py`의 `LSTMWithRevIN` 별도 클래스로 구현.  
> N1~N6: `02_normalizers.py` 전처리 → `LSTMBase` / N7: `LSTMWithRevIN` (RevIN 레이어 내장).  
> 실험 루프에서 N7만 `model_class=LSTMWithRevIN` 분기 처리. `Analysis_Plan.md` H5 섹션 반영 완료.

### D4. [H5] FD002·FD004에서 운전 조건(H3) 처리 — 미명시

**현황:**

`Hypothesis_critics.md`에서 "H3은 H5 실험의 보조 요인(FD002/FD004 특화 전처리)으로 포함. 독립 섹션 불필요"라고 결정됨.

그러나 `Analysis_Plan.md` H5 섹션은 FD002·FD004에서 운전 조건 정규화를 어떻게 처리할지 **전혀 명시하지 않음**.

**문제의 심각성:** FD002·FD004는 6가지 운전 조건(op1·op2·op3)이 센서 절대값을 수십~수백 단위로 바꾼다. 운전 조건 처리 없이 N1(fleet_minmax)을 적용하면, 서로 다른 운전 조건의 센서값이 섞여 정규화가 왜곡된다. 이 경우 H5 실험의 FD002·FD004 결과는 "정규화 방법 차이"가 아니라 "운전 조건 처리 미흡"의 효과를 측정하게 됨.

**옵션:**

| 선택지 | 방식 | 장단점 |
|--------|------|-------|
| A. **H5를 FD001·FD003만** | 단일 운전 조건 데이터셋에서만 H5 검증 | 깨끗한 비교, 범용성 주장 제한 |
| B. **고정 전처리: K-means 조건 정규화 선적용** | FD002·FD004에만 K-means 잔차(MOC 방식)를 H5 전 단계로 적용 | 현실적, H3의 "보조 요인" 역할에 부합. 단, 논문에서 명시 필요 |
| C. **H3을 H5 실험 차원으로 추가** | H3 방법 × H5 방법 교차 실험 | 가장 엄밀하나 실험 수가 급증 (7×4×4×5=560회) |

**권장:** B. "FD002·FD004에는 K-means 조건 정규화를 선행 적용한 후 H5 normalizer 비교"로 명시. 논문 §3에 "H5 실험 전처리 파이프라인" 절을 추가하면 리뷰어 지적 차단 가능.

> **✅ 결정 완료 (2026-07-02):** B 선택.  
> - FD001·FD003: raw data → H5 normalizer → LSTM  
> - FD002·FD004: raw data → K-means 잔차화(k=6, 고정) → H5 normalizer → LSTM  
> - 구현: `shared/op_condition_utils.py` 공통 유틸 (H5·H6 공유)  
> - H6 FD004 처리와 동일 로직 재사용, test 누수 없음 (train 중심점 저장·재사용)  
> - `Analysis_Plan.md` H5 Section 2-A (pre-step) + 파이프라인 주석 추가 완료.

### M1. [H6] M3 Attention-Gate의 구조적 우위 — train/test 불일치 면역

**발견 경위:** S1(test-time 클러스터 배정 절차) 설계 중 발견.

**내용:**  
M1·M2(GMM 기반)는 test 엔진 배정 시 "관측 이력의 마지막 20%"로 discriminant feature를 추출한다. 그러나 train에서 "last 20%"는 EOL 직전 구간인 반면, test에서는 관측 종료 시점 기준이므로 두 통계 간 미세한 불일치가 발생한다.

M3(Attention-Gate)는 초기 K=10 cycles만 읽어 routing weights를 end-to-end로 학습하므로, 이 train/test 불일치 문제에서 **구조적으로 자유롭다**.

**논문 활용 방안:**
- §4 모델 비교 분석에서 M3의 추가 장점으로 명시
- "Unlike GMM-based routing (M1/M2), M3's gating network relies solely on early-cycle observations, eliminating the train-test distributional mismatch in late-cycle feature extraction."
- M3가 M1·M2보다 성능이 우수할 경우 이 구조적 이점이 원인 중 하나로 서술
- M3가 열등하더라도 "초기 관측만으로 고장 모드 판별 가능한가"라는 별도 연구 질문으로 전환 가능
